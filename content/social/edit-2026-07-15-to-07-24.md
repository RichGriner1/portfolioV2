# PART 2 — Thread library (build-in-public, 3/week)

Personal account. All `status: draft` until voice-checked and locked. Post one per rotation slot; interleave so no two consecutive threads share a topic.

## Thread 1 — Token pipeline: foundations → component

**1/** I set up design tokens so an AI builds on-brand by default. My token set has three layers, and each layer only talks to the one below it. Here's the pipeline.

**2/** Layer 1: primitives. The raw values. Nothing builds against these directly.

Color ramps, one per role: primary, neutral, control, system (success, error, warning, info), and data viz if you show data.

Numbers: 0-10 by 1, 10-20 by 2, 20+ by multiples of 4.

**3/** Still primitives: typography (family, weight, letter spacing), elevation (6 or 7 shadows I assign to roles later), and motion (raw durations, fast / base / slow).

Every primitive connects up to a semantic variable in Layer 2.

**4/** Layer 2: semantic. Variables with roles: canvas, background, foreground, plus layout rules like the gap between sections or nav and content.

Set these once and you stop making the same tiny decisions every screen. That attention goes to the experience and business goals instead.

**5/** Layer 3: component. When a component needs its own value, like the gap between a label and its input, or a tag's corner radius vs a chip's, it gets a component token that maps back to a semantic.

**6/** Why three layers? I ran it with two, no component layer, and got token drift. The team couldn't hold the same look and feel across screens.

**7/** Two payoffs. Change one primitive and the whole product re-themes, because everything points back to it. Huge for white-labeling. And you get shared vocabulary: a PM can read "button-primary". Nobody outside the code can read "#3358ff".

**8/** I was building this before the AI design boom. The payoff I didn't expect: this much detail in the tokens and docs is exactly what lets AI build consistent design for you, fast. The tokens are the brief it reads.

## Thread 2 — The content engine (notes in, posts out)

**1/** I don't write social posts one at a time. I run a content pipeline: raw notes in, scheduled posts out, with a quality gate in the middle that catches my own slop. Here's the setup.

**2/** It starts with capture. End of day, I answer 2 to 4 questions into a journal file, or I feed it a meeting transcript. Raw, unedited, private. The point is catching what actually happened, not writing anything good yet.

**3/** Then an editor step shapes the strongest idea from a journal entry into a draft. One idea per draft. It asks me a clarifying question or two first, because I ramble when I talk.

**4/** A published draft gets syndicated into short-form: a LinkedIn version and a Twitter version, same substance, different shape. Still nothing is posted. It's a file on disk marked draft.

**5/** Here's the part that matters. Every draft passes two gates before it can ship. One lints my voice: banned phrases, AI tells, em-dashes. One reads for substance: is there a real lesson here, or is it a status update?

**6/** The gates don't trust each other, and neither trusts me. A post can sound exactly like me and still get killed for having no point. That distrust is the design.

**7/** Posting consistently isn't discipline. It's a backlog with gates. When next week is already written and checked, showing up is fifteen minutes of edits on a Friday. The system carries the consistency, not my motivation.

## Thread 3 — Design for the machine (AI as a first-class reader)

**1/** Most designers write their system for teammates. I write mine for teammates and the AI generating half the UI. The AI is a reader now, and it reads your token names literally.

**2/** An AI doesn't see your intent. It sees the string. Name a color token blue-500 and it reaches for blue-500 whenever it wants blue. Name it button-primary and it only uses it where a primary action lives.

**3/** So the rule I follow: name by role, not by value. surface, border-strong, text-muted. The name tells the machine what the thing is for, not what it happens to look like today.

**4/** Same for the rulebook. I keep a design.md the agent reads before it builds: what stays fixed, what it can compose, where actions live. Written where the machine can parse it, not buried in a Figma comment.

**5/** The payoff: the AI's output looks like my product instead of the framework defaults. Not because the prompt was clever. Because the system it read was specific.

**6/** Leave the AI without a brief and it fills the gaps with its defaults: same Tailwind, same rounded cards as everyone else. The written system is how your product keeps its own opinion.

## Thread 4 — One spine kills chrome drift (AFI)

**1/** I audited a fintech platform and found three screens that were basically the same page, built months apart, drifting from each other. Nobody had noticed. Here's how one spine fixed it.

**2/** The screens weren't ugly. Each one worked. But one stacked a second title, one put filters above the table, one below. Same content, different chrome on every page. The drift was between them, not in them.

**3/** A design system doesn't prevent ugly screens. It prevents duplicated ones nobody knew were there. That's the failure it's actually for.

**4/** The fix was a four-level spine: global, page, section, content. Every screen hangs off the same structure. Where the title goes, where actions go, where a section header is allowed, all decided once.

**5/** One example that stuck. Page actions used to stack under the title like a second header. We moved them inline with the title. Manu opened the reworked page and asked which line was the page. That question killed the stack.

**6/** The rule that made it hold: a header only where content actually divides. No H2 on a single-section page for consistency. Consistency is the structure repeating, not a label on every screen.

**7/** Coherence across two products came down to one spine, names that match between Figma and code, and rules short enough to fit in a dev's head while they wire a screen. Write those three down and the drift has nowhere to hide.

## Thread 5 — The motion system (a brief before any animation)

**1/** The tell of an AI-built product isn't the layout. It's the motion. Animations landing wrong, micro-interactions that shift from screen to screen because each one got its timing from a different session.

**2/** Motion drifts faster than anything else because nobody writes it down. Everyone specifies color and spacing. Almost nobody specifies how things move.

**3/** So I give motion the same treatment as tokens. A defined vocabulary: the easing curve, the durations (fast, base, slow), the stagger. Written once, in the system, not re-decided per component.

**4/** My rule for whether an animation ships: it has to show the system working. A soft, brief reveal that explains what just happened. If it's there for personality, it's decoration, and I cut it.

**5/** That kills the bounce. A CFO moving millions doesn't need a springy success check. On a high-stakes action, a deliberate beat reads as care. Bounce reads as a toy.

**6/** Motion isn't the last 5% you sprinkle on at the end. It's part of the brief, written where the AI and the next developer both read it. Decide how your product moves, or every screen decides for itself.

## Thread 6 — Component discipline (when a one-off earns systemhood)

**1/** The fastest way to bloat a design system is to promote every one-off into a shared component. The second fastest is to never promote anything. Here's how I decide.

**2/** Default: use what the library already gives you. shadcn, Base UI, PrimeNG, whatever the project runs on. A hand-rolled version of a button that already exists is just debt with your name on it.

**3/** A one-off earns promotion to a system component when two things are true: it shows up in more than one place, and it carries behavior, not just looks. Styling alone is a token job, not a component.

**4/** The test I use: would three different screens need to consult this to stay consistent? If yes, it's a system component. If it's a single screen's quirk, it stays local. Don't systematize a coincidence.

**5/** The cost of getting this wrong isn't visual. It's maintenance. Every premature component is a thing someone has to find, understand, and keep in sync forever. Systems die from that, not from missing parts.

**6/** A design system is a set of decisions about what repeats. Not a museum of every element you've ever drawn. Promote what earns it, token the rest, and let the library carry the floor.

## Thread 7 — Principles are the layer above the tokens

**1/** Tokens tell you a value is allowed. They don't tell you it's right. That gap is where design systems quietly rot, and it's why I keep a layer of principles above the tokens.

**2/** A screen can be 100% token-legal and still wrong. Every color from the palette, every spacing from the scale, and it still buries the one number the user came for. Legal isn't the same as good.

**3/** So above the tokens I keep a short set of principles. The judgment calls. Structure carries density, not whitespace. One accent, or none. A header only where content divides.

**4/** Principles are what you reach for when the tokens don't decide it for you. Two layouts both pass the token check. Which one respects the user's actual job? That's a principle question, not a token one.

**5/** I keep them short enough to actually use. A rule a dev can quote beats a principle they have to interpret. "One H1 per page, always the page header" gets wired right at 4pm on a Thursday.

**6/** A design system is two layers, not one. Tokens for what's allowed. Principles for what's right. Write only the first and you get consistency with no taste. Write both and the system decides without you in the room.
